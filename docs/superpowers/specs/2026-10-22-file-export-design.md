# Экспорт файлов из чатов ChatGPT — design

Дата: 2026-10-22. Статус: черновик на согласование.

## Зачем

chatgpt-archiver сейчас сохраняет только текст чатов. Файлы, которые видны в чате
на сайте (загруженные пользователем документы и картинки, сгенерированные
изображения, файлы проекта, файлы, созданные code interpreter), в архив не
попадают: в модели данных под них есть место (`AttachmentRecord`,
`attachmentRefs`, `chats/<id>/files/`, секция «Files» в рендере), но импорт всегда
пишет `attachments: []`. Архив без файлов неполный — по нему нельзя восстановить,
о чём шла речь, если ответ опирался на приложенный PDF или картинку.

Цель — чтобы локальный архив содержал **все файлы, которые пользователь видит в
чате**, и показывал их рядом с сообщениями, к которым они относятся.

Целевая рабочая область — та, в которую залогинен браузер в
`.remote-debug-profile/yandex` (Team workspace). Чаты, лежащие сейчас в локальном
`archive/`, относятся к другой рабочей области и через эту сессию недоступны (404 /
`user_mismatch`). Решение пользователя: архив текущей области собирается в
**новый каталог** через `--out-dir` (например `archive-team`), старый `archive/`
не трогается и не удаляется. Новый каталог должен быть в `.gitignore`, как и
`archive/` (добавить шаблон `archive-*/`), — иначе файлы пользователя попадут в git.

## Цели

1. Скачать и сохранить локально все файлы, на которые ссылаются сообщения чата:
   - вложения пользователя (`message.metadata.attachments[]`, любые mime);
   - картинки в `multimodal_text` (`image_asset_pointer` → `sediment://…`) —
     и загруженные пользователем, и сгенерированные (роль `tool`,
     `metadata.generation` / `metadata.dalle`);
   - файлы проекта (`metadata.attachments[]` у system-сообщений проектных чатов);
   - файлы инструментов (`metadata.attachments[]` у `tool`-сообщений, например
     картинки, созданные code interpreter);
   - ссылки `sandbox:/mnt/data/...` в тексте ответов ассистента.
2. Показать файлы в HTML-архиве у соответствующего сообщения: картинки — inline,
   остальное — карточкой (имя, размер, тип, ссылка на локальную копию).
3. Повторный запуск не скачивает уже скачанное.
4. Ошибка одного файла не роняет прогон: файл получает статус, остальное
   продолжается, в конце — сводка.

## Не цели

- Экспорт canvas / textdocs.
- Превью страниц документов (`sediment://<hash>#file_X#p_0….jpg`): сохраняем
  только сам документ `file_X`, не картинку-превью.
- Файлы проекта, на которые не ссылается ни один чат (вкладка «Files» проекта как
  таковая).
- Инкрементальный fetch чатов по `update_time`, ретраи на 429, починка выборки
  чатов с `is_starred` / `is_archived` — отдельные задачи.
- Незакоммиченная правка `src/renderer/render.ts` (обёртка `code` в python-fence)
  к экспорту файлов не относится. Решение пользователя: **до начала этой работы**
  поправить её — язык fence брать из `content.language` (сейчас всегда `python`,
  а из 229 `code`-сообщений 207 — JSON-вызовы инструментов с `language: "json"`;
  при `unknown`/отсутствии — fence без языка) — и закоммитить отдельным коммитом.
  Экспорт файлов строится поверх этого коммита.

## Анти-цели (провал, даже если «работает»)

- Подписанные ссылки (`download_url` с `sig=`), cookies или токены попадают в
  логи, в `manifest`, в HTML или в сырые JSON на диске.
- Имя файла из ответа сервера даёт записать файл вне каталога архива
  (`..`, абсолютные пути, `/mnt/data/...`-префиксы, зарезервированные имена Windows).
- Каждый запуск заново скачивает все файлы.
- Один неудачный файл обрывает весь `fetch`.

## Проверенные факты (spike 2026-10-22, живая сессия)

Проверено на 7 видах ссылок в текущей рабочей области; все скачались, magic bytes
совпали с типом (JPEG, PNG, PDF, DOCX, ZIP).

- **Обычные файлы**: `GET /backend-api/files/download/{file_id}?conversation_id={chat_id}&inline=false`
  (так же работают `/files/download/{id}` и `/files/{id}/download`) →
  JSON `{ status: "success", download_url, file_name, mime_type, file_size_bytes,
  creation_time, metadata, no_auth_user_upload }`.
- **Sandbox-ссылки**: `GET /backend-api/conversation/{chat_id}/interpreter/download?message_id={message_id}&sandbox_path={url-encoded /mnt/data/...}`
  → JSON той же формы (без `file_size_bytes`).
- `download_url` — same-origin `https://chatgpt.com/backend-api/estuary/content?id&fn&cd&ts&p&cid&sig&v`.
  Скачивается curl'ом **с cookies сессии и user-agent браузера**, без
  `authorization`. Без cookies — 403 JSON (39 байт).
- Получение JSON-метаданных требует тех же заголовков, что и уже используемые
  `backend-api` запросы (`authorization`, `chatgpt-account-id`, `oai-*`) — их
  проект уже захватывает в `captureApiHeaders`.
- Извлечение file id из указателей:
  `sediment://file_<hex>` → `file_<hex>`;
  `sediment://<hash>#file_<hex>#p_…` → `file_<hex>` (это исходный документ);
  в `metadata.attachments[].id` id уже в виде `file_<hex>`.
- `file_name` у файлов инструментов приходит с путём песочницы
  (`user-…/…/mnt/data/QA_contact.png`) — нужно брать basename.
- Кириллица в `content-disposition` корректна только в `filename*`; имя берём из
  JSON `file_name`, не из заголовка.
- Один и тот же file id встречается в нескольких сообщениях и чатах (картинка
  во вложении и в `multimodal_text`; файлы проекта во всех чатах проекта).
- `message_id` для `interpreter/download` — id **assistant**-сообщения, в тексте
  которого стоит ссылка `sandbox:` (так проверено в spike, скачивание прошло).
- Скан всех 22 чатов текущей области:
  - в JSON чатов нет подписанных ссылок (`sig=`, `estuary/content` — 0 вхождений;
    в старом `archive/` тоже 0), значит сырые JSON чистить не нужно;
  - `asset_pointer` встречается только со схемой `sediment://` (103 раза),
    `file-service://` и id вида `file-…` нет;
  - в чате с 19 вложениями инструментов (`/mnt/data/...` в имени) и 8
    `sandbox:`-ссылками ни один путь не совпал — это разные файлы, склеивать их не
    нужно.
- Байты через CDP `Runtime.evaluate` (base64) для файла ~4 МБ не прошли — браузерный
  путь для бинарных данных через `page.evaluate` не годится.
- На Yandex-профиле Playwright `connectOverCDP` в spike иногда зависал, а
  `context.newPage()` падал (`_page` undefined). Текущий `session.ts` использует
  существующую вкладку (`context.pages()[0]`), это не трогаем, но учитываем как
  риск при проверке.

## Решения

### Где и когда скачивать

Скачивание — на шаге **fetch**, сразу после сохранения JSON чата, в той же
браузерной сессии: подписанные ссылки короткоживущие, а `import` работает офлайн.
`import` только связывает уже скачанные файлы с сообщениями и рендерит.

### Извлечение ссылок — одна чистая функция

Новый модуль (предлагаю `src/network/fileRefs.ts`) с функцией, которая по JSON чата
возвращает список ссылок на файлы:

```ts
type FileRefKind = "attachment" | "image" | "sandbox";
interface FileRef {
  key: string;            // file id ("file_…") или "sandbox:<chatId>:<messageId>:<path>"
  kind: FileRefKind;
  chatId: string;
  messageId: string;      // id узла mapping, где встретилась ссылка
  role: ChatRole;         // роль автора этого сообщения
  fileName?: string;      // из attachments[].name или basename sandbox-пути
  mimeType?: string;
  sizeBytes?: number;
  sandboxPath?: string;   // только для kind = "sandbox"
  generated?: boolean;    // image с metadata.generation/dalle
}
```

Её используют и fetch (что скачать), и import (к чему привязать). Тестируется на
маленьких обезличенных фикстурах.

Ссылки на sandbox ищутся регэкспом `sandbox:(/mnt/data/[^)\s"]+)` в текстовых
частях **assistant**-сообщений (в коде и выводе инструментов `/mnt/data` встречается
как путь внутри кода, его не трогаем).

### Хранилище сырых файлов

```
archive/network/files/
  manifest.json
  <key-dir>/<safe-file-name>
```

- `<key-dir>` — file id как есть (`file_…`); для sandbox — короткий хеш ключа
  (`sandbox-<shortHash>`), потому что путь длинный и с недопустимыми символами.
- `<safe-file-name>` — basename `file_name`, очищенный от символов
  `<>:"/\|?*` и управляющих, без зарезервированных имён Windows (`CON`, `NUL`, …),
  обрезанный до разумной длины с сохранением расширения; если пусто —
  `file` + расширение из `mime_type`.
- `manifest.json` — объект `key → запись`:
  `{ key, kind, fileName, localPath (относительно archive/network/files), mimeType,
  sizeBytes, sha256, status, error?, downloadedAt?, seenIn: [{chatId, messageId}] }`.
  Без `download_url`, без заголовков.

Статусы — существующий `AttachmentStatus`: `downloaded` | `failed` | `missing` |
`skipped`. `missing` — сервер вернул 404 / `status` ≠ `success` (файл удалён или
истёк). `failed` — прочие ошибки (сеть, 401/403, неожиданный ответ). `skipped` —
запуск с `--skip-files`.

### Идемпотентность

Файл не скачивается заново, если в манифесте `status = downloaded`, файл на диске
существует и его размер совпадает с `sizeBytes` (если размер известен). `failed` и
`missing` при следующем запуске пробуются снова.

### Транспорт

1. Метаданные: существующий `requestJson` (curl с захваченными заголовками,
   fallback в браузер на 401/403) — для `files/download/{id}?conversation_id=…`
   или `interpreter/download?…`. `referer` — URL чата, `chatgpt-project-id` — как
   для запроса самого чата.
2. Байты: новая функция в духе `runCurlRequest`, но с `-o <tmp-файл>` вместо
   чтения stdout; заголовки — только `cookie` и `user-agent` из захваченных.
   Пишем во временный файл рядом и переименовываем после успеха; sha256 считаем
   по файлу на диске.
3. Браузерного fallback для байтов нет (через `page.evaluate` большие файлы не
   проходят). Если curl получил 403 — файл `failed`, прогон продолжается.

Скачивание последовательное (как и запросы чатов сейчас).

### Импорт

- По каждому чату: `extractFileRefs(payload)` + `manifest.json` →
  `AttachmentRecord` на каждую уникальную пару (чат, key):
  `attachmentId = key`, `messageId` — первое сообщение, где ссылка встретилась
  (с учётом правил привязки ниже), `localPath` — путь копии внутри чата.
- Скачанные файлы **копируются** в `archive/chats/<chatId>/files/<safe-file-name>`
  (каждая папка чата самодостаточна; рендер уже ссылается на `./files/…`).
  Коллизии имён внутри одного чата — суффикс ` (2)`, ` (3)`.
- `messages[].attachmentRefs` заполняются (`relation` = kind, `ordinal` — порядок
  в сообщении), `ChatIndexEntry.attachmentCount` — число файлов чата.
- Файлы со статусом не `downloaded` тоже попадают в `attachments.json` (без копии),
  чтобы рендер показал заглушку.

Правила привязки к сообщениям в HTML:

- **user**-вложения и картинки → к сообщению пользователя.
- **Сгенерированные картинки** (`tool`-сообщения) и файлы инструментов → к группе
  ассистента того же хода (`turn_exchange_id`; если его нет — к ближайшей
  следующей группе ассистента). Сейчас импорт отбрасывает `tool`-сообщения, а рендер
  их пропускает — нужно сохранять `tool`-сообщения, у которых есть ссылки на файлы,
  и в рендере переносить их вложения в группу ассистента, не показывая их текст.
- Сообщения, где есть только картинка без текста, больше не отбрасываются
  (сейчас `keep = false` при пустом тексте).
- **Файлы проекта** (system-сообщения) → отдельная секция «Файлы проекта» в шапке
  чата, а не у конкретного сообщения (system-сообщения не рендерятся).
- **Sandbox**-ссылки → к сообщению ассистента, где они встретились; в его HTML
  ссылка `sandbox:/mnt/data/x` переписывается на локальную `./files/x`. Если файл
  не скачан — ссылка остаётся текстом с пометкой статуса.

### Рендер

- Картинки (`mimeType` начинается с `image/`) — `<img loading="lazy">` в ссылке на
  оригинал, с ограничением ширины по CSS.
- Остальные — карточка в существующей секции «Files»: имя, размер в человеческом
  виде, тип, ссылка «Открыть локальную копию».
- Не скачанные — карточка без ссылки со статусом (`missing` — «файл недоступен на
  сервере», `failed` — «не удалось скачать»).
- Все строки из ответа сервера — через `escapeHtml`, ссылки — через
  `encodeURIComponent` имени (как сейчас).

### CLI

- `fetch` / `run` по умолчанию скачивают файлы.
- `--skip-files` — не скачивать (файлы получают `skipped`, если их ещё нет в
  манифесте; уже скачанные остаются).
- В конце `fetch` — строка сводки: `Files: N downloaded, M skipped (cached),
  K failed, L missing`.
- Справка (`printHelp`) и README обновляются.

### Логи

Логируем key (file id или `sandbox-<hash>`), имя файла, статус и HTTP-код. Никогда —
`download_url`, query-параметры, заголовки, cookies.

## Проверка

- Юнит-тесты (`node --test`, как сейчас): извлечение ссылок по всем видам из
  фикстур (включая составной указатель и sandbox-ссылку), очистка имён файлов
  (кириллица, `..`, `CON`, путь песочницы, пустое имя), решение «скачивать / из
  кэша» по манифесту, привязка вложений к сообщениям при импорте, разметка рендера
  (inline-картинка, карточка, заглушка, переписанная sandbox-ссылка).
- Реальный прогон: `run --cdp-url http://127.0.0.1:9222 --out-dir archive-team` по
  текущей рабочей области → файлы в `archive-team/network/files`, открыть в браузере `index.html` и чат
  с картинкой, сгенерированной картинкой, PDF и sandbox-zip; проверить, что второй
  запуск ничего не скачивает заново; проверить grep'ом, что в `archive-team/` нет
  `sig=`; `git status` не показывает файлов из `archive-team/`.

## Решения автора дизайна (не согласованы отдельно — проверить при чтении)

- Скачивание на шаге fetch, а не import (из-за короткоживущих подписанных ссылок).
- Файлы копируются в папку каждого чата, а не ссылаются на `archive/network/files`.
- Нет браузерного fallback для байтов: 403 от curl → `failed`.
- Файлы проекта — секцией в шапке чата, а не у сообщения.
- Sandbox-ссылки и вложения инструментов — разные ключи, без склейки (подтверждено
  сканом).
- Устаревшие указатели `file-service://file-…` распознаются тем же регэкспом
  (`file[-_][A-Za-z0-9]+`) и качаются тем же endpoint'ом в режиме best-effort: в
  текущей области их нет, живьём не проверено; неудача → `failed`/`missing`.
- Если один файл упоминается в нескольких сообщениях чата, в HTML он показывается
  один раз — у первого сообщения по правилам привязки (рендер группирует по
  `AttachmentRecord.messageId`, переделывать на `attachmentRefs` не нужно).
- Скачивание последовательное, без параллелизма.

- Вёрстка карточек и картинок в пределах существующего CSS.
- Как именно рендер находит группу ассистента для `tool`-вложений, если правило
